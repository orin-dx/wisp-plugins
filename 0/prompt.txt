## Why this exists

A Callisto maintainer (Callisto is a release tool) kept writing poor changesets. We tried `courier:changeset-analyzer` on a real diff (a feature that links each change in a release PR to the pull request that added it) and the agent's own rules got in its way:

- **Hard length caps.** The `changeset@2` schema has `summary.maxLength: 200` with "one clause for patch, one sentence for minor". The agent and `courier/changeset` skill repeat it. The agent had to choose between the visible change and a scripting detail, and left a real user-facing limitation (changesets pushed directly get no link) in `reasoning`, which is never forwarded.
- **Flat output.** `summary` is one string, so it cannot carry a lead line plus sections, bullets and sub-bullets.
- **Per-diff granularity.** The agent splits a diff into topics. Real features span several PRs, and some PRs need no changeset at all. Nothing lets it say "update the existing entry" or "no changeset needed".
- **No "why it matters".** The agent's own backstory complains about notes that say what changed but not why, but the output contract doesn't require it.
- **Semver table gaps.** `shared/references/delivery/changesets.md` has rows for agents, skills and schemas only. It has none for a CLI's flags, output formats or serialized files, so the agent mapped by analogy.
- **Reference not loading.** `load_first` names `shared/references/delivery/changesets.md`. In source this resolves through a `plugins/courier/shared -> ../../shared` symlink. The installed Claude copy (`~/.claude/plugins/cache/orin-dx-agent-plugins/courier/3.0.3/`) has no `shared/` at all, so the reference may never load.

## What the maintainer wants (use these as the design goals)

Changelog entries communicate value clearly to users who are upgrading, scripting or setting up. They are easy to scan and still give depth for readers who want it.

- **No hard length targets.** Prescriptive limits don't produce value with LLMs. Replace them with judgment: detail proportional to what the reader needs.
- **Layered structure when there is enough to say:** a lead line stating the value, then bullets, with sub-bullets for depth, grouped under audience sections where useful (for example what you see, scripting, upgrading). A one-line entry is fine when that is all there is.
- **Say what it is, why it helps, and what to do.** Name the visible thing (a "link", a "label", a "flag"), where it appears, and the action if any. Vague verbs like "identifies" or "says" fail this test.
- **State limits that users will hit.** They belong in the entry, not in a scratchpad.
- **One entry per user-visible outcome, not per PR.** A feature across several PRs updates one entry. A change that is not user-visible, or fixes something not yet released, gets no changeset. The agent should be able to recommend this.
- **Consistent voice** across entries, following `shared/references/authoring/voice.md`.
