The pipeline as a spec-verification system

The agents aren't just a fancier way to write code. They separate concerns that I've been conflating:

graph-intake → graph-clarifier     # WHAT we're building (requirement@1)
canon-drafter → canon-auditor      # IS IT UNAMBIGUOUS (spec@1 with testable criteria)
canon-exit-gate                    # ADVERSARIAL GATE before a line of code exists
vector-planner → vector-challenger # HOW to build it (plan@1 in dependency order)
lambda-recon → lambda-implementer  # BUILD with red-green per task
lambda-reviewer                    # REVIEW each commit before the next task starts
lambda-exit-gate                   # ADVERSARIAL re-read from scratch at the end
canon-verifier                     # DRIFT CHECK spec vs. code after the fact

The critical property: every agent after canon-exit-gate reads from scratch. It doesn't inherit my context. If I implemented something wrong, the exit gate finds it not because it trusts me but because it independently re-reads the spec and the code and checks each criterion.

What this means for a semantic model specifically

A semantic model is a perfect fit for canon because:

- The concepts (PackageId, VersionPlan, etc.) map directly to spec@1 documents
- The invariants become acceptance_criteria — testable propositions
- canon-auditor would have caught our drift early: "this criterion is vague — 'bare names match across ecosystems by design' — what exactly does that mean? Under what conditions? What's the counterexample?"

The spec@1 for PackageId would look like:

acceptance_criteria:
  - id: PKG-1: Bare("foo").matches(Prefixed(Cargo, "foo")) → true
  - id: PKG-2: Prefixed(Cargo, "foo").matches(Prefixed(Npm, "foo")) → false
  - id: PKG-3: [[package]] rule application is specificity-ordered (prefixed > bare)
  - id: PKG-4: A bare rule matching packages in multiple ecosystems emits a diagnostic

Each of those is independently verifiable. lambda-reviewer after each commit would check: does this commit address PKG-3? Does it break PKG-1?

## Track E: PackageId Specificity Ordering + Cross-Ecosystem Diagnostic

### Design decision (already made — implement exactly this, no deviation)

Do NOT change `PackageId::matches()`. The bare-matches-all-ecosystems
behavior is correct for napi-rs polyglot packages. The two fixes are:

**Fix 1 — Specificity ordering in rule application**

File: `crates/callisto-graph/src/walk.rs`

Find the `[[package]]` rule lookup (a `.find()` call over `cfg.packages`).
Replace first-match-wins with specificity-ordered matching:

A prefixed PackageId rule (pattern like `cargo:foo` or `npm:foo`) beats a
bare PackageId rule (pattern like `foo`) when both match the same package,
regardless of which rule appears first in callisto.toml.

Algorithm:
1. Collect ALL matching `[[package]]` rules for this package
2. If any are prefixed matches, use the first prefixed match (declaration order)
3. If none are prefixed matches, use the first bare match (declaration order)
4. If no matches, result is None

Read `crates/callisto-model/src/identity.rs` to understand the PackageId
type. You may need to add `is_prefixed()` / `is_bare()` methods if they do
not exist. Keep any additions minimal.

`cfg.packages` is typed as `Vec<(PackageId, PackageConfig)>` — read
`crates/callisto-graph/src/config/resolve.rs` to confirm.

**Fix 2 — Cross-ecosystem diagnostic**

In `ManifestWalkResolver::build` in `walk.rs`, after the packages loop
completes (before the edges loop):

For each bare-pattern entry in `cfg.packages`, collect the set of distinct
ecosystems among all packages it matched. If the set contains more than one
ecosystem, push to `diagnostics` (already exists in scope):

Message format:
"[[package]] rule `{pattern}` matches packages in multiple ecosystems
({ecosystem_list}); use an ecosystem-prefixed pattern like `cargo:{name}` if
you intend only one ecosystem"

`[[package-set]]` rules (in `cfg.package_sets`) are EXEMPT from this
diagnostic — multi-ecosystem matching is their explicit, intentional purpose.

To implement this: during the packages loop, track a
`BTreeMap<PackageId_pattern_string, BTreeSet<Ecosystem>>` of which ecosystems
each bare rule matched. After the loop, check that map to emit diagnostics.

The `diagnostics` vec is already declared at the top of `build()` and is
returned in the final `ManifestWalkResolver { ... }` struct.

### Acceptance criteria (encode ALL of these into spec@1)

- E-1: When `callisto.toml` contains `[[package]] match = "foo"` followed by
  `[[package]] match = "cargo:foo"`, the package `cargo:foo` uses the
  `cargo:foo` rule's config (not the `foo` rule's config)
- E-2: When `callisto.toml` contains `[[package]] match = "cargo:foo"`
  followed by `[[package]] match = "foo"`, the package `cargo:foo` still uses
  the `cargo:foo` rule's config (specificity beats declaration order)
- E-3: When only bare rules exist, first-match-wins (declaration order)
  is preserved unchanged
- E-4: When only prefixed rules exist, first-match-wins (declaration order)
  is preserved unchanged
- E-5: A bare `[[package]]` rule that matches packages in exactly one
  ecosystem emits no diagnostic
- E-6: A bare `[[package]]` rule that matches packages in two or more
  ecosystems emits exactly one diagnostic, naming the pattern and the
  matched ecosystems
- E-7: `[[package-set]]` rules never emit the cross-ecosystem diagnostic
- E-8: `PackageId::matches()` behavior is unchanged end-to-end (do not
  modify the method itself)
