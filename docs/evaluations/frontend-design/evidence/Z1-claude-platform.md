# Z1: Anthropic agent platform capabilities vs. a 10-plugin / ~44-agent architecture

Researched 2026-10-17. Tags: [P] primary page read in full or in the relevant part; [S] search summary only; [U] unverified.
Caveat: WebFetch summarises pages through a small model, so exact numbers are [P] to the page as summarised; hooks (273k chars) and subagents (111k chars) pages were read only for the first ~100k chars.

Target architecture assumed: 10 plugins; ~44 role-specific agents each embedding a byte-identical ~290-line constitution; schema-first JSON handoffs; default-fail binding gates with retry caps; orchestration by skills that spawn subagents.

## 2. Features that make parts of the architecture redundant or risky

1. **290-line constitution copied into 44 agent files.** Redundant given `skills:` preload, shared reference files loaded via progressive disclosure, and `omitClaudeMd`; risky because cache sharing is per (model, effort, type, tools) [P], so byte-identity buys little; and the 15,000-token agent-description cap [P] plus constitution drift risk (a byte-identity validator becomes load-bearing). Anthropic's own guidance: "minimal set of information that fully outlines expected behavior" [P: effective-context-engineering]. Counterpoint: Fable 5.1 follows existing prompts "without changes" [P], so shrinking is a quality-eval question, not a forced move.
2. **Prompt-enforced "default-fail" gates.** A gate agent is a model asked to be skeptical. Anthropic's harness post found self/peer evaluators need heavy calibration and drift lenient [P: harness-design-long-running-apps]; the multi-agent blog names the "early victory problem" for verifiers [P]. A Stop/SubagentStop hook running a validator is deterministic and cannot be talked out of failing.
3. **Retry caps expressed in prose.** Hooks and workflows can count; the model cannot reliably. Workflows cap structured-output retries at 5 natively [P].
4. **Skills that spawn subagents turn by turn.** Docs state Claude is then the orchestrator and every result lands in its context window; workflows move loops and intermediate results into script variables [P]. Role-pipeline orchestration by a model carries the "orchestrator failure" modes (duplicate work, vague delegation) [P].
5. **Role-by-pipeline-stage agents.** Anthropic's multi-agent guide names splitting by problem type (planner/implementer/tester/reviewer) as the anti-pattern; prefers context-centric decomposition [P: claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them]. 44 role agents is exposed to this critique; the genuinely justified splits are verifier/adversary (clean context, minimal transfer) and parallel fan-out.
6. **Depth limits and plugin-agent restrictions.** Depth 3 default; plugin agents lose hooks/mcpServers/permissionMode [P]. Nested agent-calls-agent designs break or silently lose controls.
7. **Staleness of encoded assumptions.** "Every component in a harness encodes an assumption about what the model can't do... worth stress testing"; V2 harness removed sprint decomposition when Opus 4.6 arrived, cutting 6 h/$200 to 3.8 h/$125; evaluator value became conditional on task difficulty [P]. The agents split for 2024-2025 reliability limits are the prime suspects after Opus 5.5/Fable 5.1.
8. **Model-behaviour changes that break prompts.** Forced tool use rejected; thinking blocks bound to model and conversation (editing earlier turns invalidates them, 400 on new accounts); default effort changed (Opus 5.5 medium) [P]. Any agent that pins an old model, sets budget_tokens, or relies on `tool_choice` will fail.
9. **Agent teams enablement side-effect** (named subagents become teammates) [P].

## 3. Platform features the architecture does not use

- `claude plugin eval` with no-plugin baseline (Δ) in CI [P]; per-case 3 runs, llm/regex/tool_used/file graders.
- Plugin-level hooks as deterministic gates (schema validation on SubagentStop; PreToolUse path fences; TaskCompleted blocking) [P].
- `context: fork` + `agent:` in SKILL.md; `!`cmd`` dynamic context injection for deterministic recon (replaces a haiku "recon" agent for pure enumeration: git status, file lists, manifest) [P].
- Dynamic workflows shipped in the plugin (`workflows/`) with `agent({schema})`, `pipeline`/`parallel`, resumability, 16-way concurrency [P].
- `bin/` executables on PATH (validators, schema checkers) and `${CLAUDE_PLUGIN_DATA}` for retry counters [P].
- `maxTurns` + `SendMessage` resume for repair loops with context retained [P].
- `isolation: worktree` for implementers; `memory:` for agents that accumulate conventions [P].
- Per-agent `effort` and `autoCompactWindow`; `experimental.cacheTtl: 1h` / `subagentPromptCacheTtl` for multi-minute fan-outs [P].
- Plugin `dependencies` to share one constitution/schema plugin across the 10 plugins instead of copying [P].
- Routines for scheduled drift/audit runs [P: agents page].
- Task budgets, per-message effort, compaction-on-demand (API) [P: opus-5-5 whats-new].

## 4. Evidence on multi-agent vs single-agent

| Claim | Evidence | Tag |
|---|---|---|
| Multi-agent beat single-agent on breadth research | Opus 4 lead + Sonnet 4 subagents beat single-agent Opus 4 by 90.2% on Anthropic's internal research eval | anthropic.com/engineering/multi-agent-research-system [P] |
| Cost | Agents ~4x chat tokens; multi-agent ~15x (research system); later guidance: 3-10x vs single agent for equivalent tasks | same [P]; claude.com blog [P] |
| Where it works | Heavy parallelization, information exceeding one context, many complex tools, high-value tasks | research-system [P] |
| Where it does not | "Domains that require all agents to share the same context or involve many dependencies between agents"; most coding tasks ("LLM agents are not yet great at coordinating and delegating in real time") | research-system [P] |
| Three justified reasons | Context protection (>~1,000 tokens of irrelevant output), parallelism ("thoroughness, not speed"), specialization (agents with 20+ tools err); otherwise coordination costs exceed benefit | claude.com blog [P] |
| Anti-pattern | Splitting by role/problem type creates agents that spend more tokens communicating than working; decompose by context | claude.com blog [P] |
| Verifier failure | Verifiers declare victory after 1-2 tests; require explicit full-suite instructions | claude.com blog [P] |
| Orchestrator failures observed | 50+ subagents for simple queries, endless searches, duplicate work from vague delegation, sequential rather than parallel | research-system [P] |
| Simplicity default | "Find the simplest solution possible, only increasing complexity when needed"; frameworks obscure prompts; agents carry "compounding errors" risk | building-effective-agents [P] |
| Self-evaluation | Models praise their own mediocre work; a separate tuned evaluator is more tractable; but evaluator is conditionally valuable as models improve (essential at capability boundary, overhead otherwise) | harness-design-long-running-apps [P] |
| Single vs specialist open question | Anthropic's own long-running-harness post says it is "unclear" whether one generalist beats testing/QA/cleanup agents | effective-harnesses-for-long-running-agents [P] |
| Cost of harness | Solo agent 20 min/$9 vs full 3-agent harness 6 h/$200 vs simplified harness 3.8 h/$125 (quality was higher in harness, per the post's framing) | harness-design [P] |
| Claude Code docs | Teams "use significantly more tokens"; "for sequential tasks, same-file edits, or work with many dependencies, a single session or subagents are more effective"; subagents for side tasks that would flood the main context | agent-teams, agents pages [P] |
| Model-level shift | Opus 5.5 testimonial: "delegates to subagents far more effectively" (customer quote, not controlled) | anthropic.com/claude-opus-5-5 [P, anecdotal] |
| Fable 5.1 guidance | Do not make the lead block on subagents; let it continue while they run (lower time at similar quality/tokens/cost on coding tasks) | prompting-claude-fable-5-1 [P] |
| Context rot | Recall degrades as context grows; sub-agents with clean contexts returning 1-2K-token summaries is the supported pattern | effective-context-engineering [P] |
| Eval guidance | Grade outcomes not paths; start with ~20 queries; use pass@k / pass^k; clean environment per trial; human transcript review | demystifying-evals; research-system [P] |

No source found that tests 40+ role-specialised agents in a linear plugin pipeline against a single agent with the same instructions [U]. The architecture's benefit is therefore untested by vendor evidence; the vendor's own test method (`claude plugin eval` with-arm vs without-arm) is the way to measure it.
